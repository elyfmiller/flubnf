# G01 test-hub-leak: proposal (B)
Base: origin/dev e283835

## TS-01 (also: MO-21)
- Reproduced: yes. With the hub cloned at `~/GitHub/FluSight-forecast-hub` and no `FLUBNF_HUB` in the environment, the five named tests fail exactly as reported (`'vintage' == 'realtime'`; the audit test's flash reads "Not run: select a location"; the anchor test's first `<script>` after the anchor line is the Data issues box's, not the anchor script's). All five pass with `FLUBNF_HUB=/nonexistent`. MO-21 is the two `test_research_run` cases among them.
- Root cause: `app/tests/conftest.py` pins `FLUBNF_STATE_DIR` at import but not `FLUBNF_HUB`, so `flubnf/settings.py` resolves `HUB` to the default checkout and every module that copies it (`app.core.data`, `scoring`, `reported`, the engines) reads the clone. Three leaks: (1) `data.newest_week()` includes `live_newest_week()`, the clone's live target file (2026-10-17), so `/run` records a 2098 forecast date as `vintage` (`routes/forecast.py`, "mode follows the anchor") in `test_research_run` and `test_resume_rerun`; (2) in `test_audit_fixes`, `vintages` is patched but the real archive still holds 2026-02-14, so `observed_source` succeeds and the refusal moves on to the locations check; (3) in `test_data_source`, `_newest_report()` (the Data tab's check through `app.core.reported`) finds the clone's live file and renders the Data issues box, whose script sits between the anchor line and the anchor script. The same happens when the shell exports `FLUBNF_HUB` to a real clone (setup.sh writes that export into `.flubnf.env`).
- Fix: `app/tests/conftest.py` sets `os.environ["FLUBNF_HUB"]` to `TEST_STATE / "no-hub"` (never created) right after `FLUBNF_STATE_DIR`, before any import of `flubnf.settings`, so the suite is hub-free whatever the machine or the shell has, exactly as CI is; pytest loads this conftest at startup for `pytest tests/ app/tests/` too (the same mechanism `FLUBNF_STATE_DIR` relies on). The three tests that compared the vendored copies against a real clone through `settings.HUB` or `settings.ARCHIVE` now opt in through `FLUBNF_TEST_HUB`, as `test_hubcheck` already does: `test_core::test_analogue_engine_runs_real_vintage` (repoints `data.ARCHIVE` and the engine's `LOCATIONS`), `test_model_metadata::test_the_vendored_schema_equals_the_hub_clone_when_there_is_one`, `tests/test_sihrs_fit::test_vendored_locations_matches_hub`. `tests/README.md`: the "this machine's hub and engine" row becomes "this machine's engine" plus an `FLUBNF_TEST_HUB=...` row for the hub-reading cases; the skip table says so. CI, `.githooks/pre-push` and the docs that say `FLUBNF_HUB=/nonexistent` stay as they are (still true, now redundant).
- Tests: new `app/tests/test_suite_hub.py` with `test_the_suite_reads_no_hub_clone_at_the_default_path` (settings.HUB is the pinned path, it does not exist, it is not `~/GitHub/FluSight-forecast-hub`, and `data.HUB`, `scoring.HUB`, `data.ARCHIVE` are the same pin) and `test_without_a_hub_the_live_file_has_no_week` (`data.live_newest_week()` is None: the exact leak). Both fail on dev with a clone at the default path. The three opt-in tests were run with `FLUBNF_TEST_HUB` pointing at this container's sparse clone (target-data, auxiliary-data, hub-config): they pass; `test_hubcheck`'s hub cases run and pass the same way.
- Checked: the five tests plus `test_suite_hub`, `test_hubcheck`, `test_core`, `test_model_metadata`, `tests/test_sihrs_fit` in four configurations: env unset with the clone at the default path (pass; hub cases skip as in CI); `FLUBNF_HUB` exported to the real clone (pass); `FLUBNF_TEST_HUB` opt-in (pass, hub cases run); `pytest tests/test_sihrs_fit.py` alone (no conftest: skips, as it should without the opt-in). `ruff check --select F821,F823,F811,F401` (the gate `test_ui_layout` runs) clean on the changed files and `app/ui`. Full suite with the clone at the default path and no env: running, counts in a follow-up commit.
- Risk: tests only; no app code. Invariance check: no. What changes outside the five: hub-reading cases that used to run whenever a clone sat at the default path now need `FLUBNF_TEST_HUB` (the README says so); `test_playback`'s two `_real_ok` cases also need a full clone (model-output) plus sealed seasons and go through `settings.HUB` at import, so they skip unless the hub is pinned at that point; I left them (a process-wide opt-in would bring the leak back for the five). Windows: the pin is a path under the suite's temp folder, no POSIX literal; CRLF and encoding untouched.
- For Ely: none. (One note, not a decision: `tests/README.md` now documents `FLUBNF_TEST_HUB`; `docs/LAUNCHERS.md` line 77 still says CI sets `FLUBNF_HUB=/nonexistent`, which stays true.)
