  - hub present, no env: 3437 passed, 151 skipped, 7 failed (the 5 above + 2 doctor checks that fail only because this container's default python3 is 3.13; on 3.12 they pass).

- Root cause: `app/tests/conftest.py` pins FLUBNF_STATE_DIR at import but not FLUBNF_HUB, so `flubnf/settings.py` `HUB = _checkout("FLUBNF_HUB", ...)` falls back to `~/GitHub/FluSight-forecast-hub`. The tests patch `app.core.data.HUB/ARCHIVE` or `data.vintages`, but other readers bind the hub at import (`scoring.HUB`, `playback.HUB`, the newest-week report and data-issues box on /forecast, the run's realtime/vintage resolution), so the real newest week leaks in. Example: in test_data_source the real hub adds the newest-week and data-issues partials, whose own `<script>` makes the test's `split("</script>")` cut the anchor script short; in the run tests 2098/2025 dates resolve against the real archive and record "vintage".
  Patching the five tests one by one would leave the class open (any module that imports settings.HUB leaks the next one), so the fix is the pin the hint names.
- Fix:
  1. `app/tests/conftest.py`: at import, right after FLUBNF_STATE_DIR and before any app import, `NO_HUB = TEST_STATE / "no-hub"; os.environ["FLUBNF_HUB"] = str(NO_HUB)`, with a docstring bullet. A folder under the suite's own temp state rather than "/nonexistent": it never exists, and if a test ever wrote to the hub it would land in the temp folder (cleaned at exit) instead of creating /nonexistent (we run as root here; C:\nonexistent on Windows). pytest loads this conftest at startup for `pytest tests/ app/tests/` (and for testpaths), so tests/ is pinned too in a full run; checked: tests/ modules that import flubnf.settings at module level are collected first and settings.HUB is still the pinned path.
  2. Tests that compare against a real clone opt in through FLUBNF_TEST_HUB (test_hubcheck already did): `test_core::test_analogue_engine_runs_real_vintage` (points `core_data.ARCHIVE` and `analogue.LOCATIONS` at the clone, as test_hubcheck's real-run test does), `test_model_metadata::...equals_the_hub_clone...`, `tests/test_sihrs_fit::test_vendored_locations_matches_hub`; test_hubcheck drops its FLUBNF_HUB fallback (dead under the pin) and its docstring says so.
  3. `tests/README.md`: the "this machine's hub and engine" row now says the suite never reads the hub, plus a row for `FLUBNF_TEST_HUB=~/GitHub/FluSight-forecast-hub .venv/bin/python -m pytest`; the "What skips" table splits always-skipped hub cases from the FLUBNF_TEST_HUB ones.
- Tests: added `app/tests/test_state_isolation.py::test_no_test_reads_this_machines_hub_clone` (FLUBNF_HUB is a missing folder inside the suite's state folder, settings.HUB is it, and a subprocess sees the same). It fails on dev both with a hub clone present (KeyError, FLUBNF_HUB unset) and under CI's FLUBNF_HUB=/nonexistent (not the suite's own folder), and passes with the fix. Opt-in checked: with FLUBNF_TEST_HUB=~/GitHub/FluSight-forecast-hub, test_core's real-vintage run, the schema check, the locations check and test_hubcheck's clone cases run and pass (one hubcheck case skips: the sparse clone has no FluSight-ensemble files).
  Full suite on the prototype (Python 3.12, as CI): hub present with no env, 3441 passed, 155 skipped, 0 failed; FLUBNF_HUB=/nonexistent, 3441 passed, 155 skipped, 0 failed; the SKIPPED lists are identical line for line. (Against dev's CI-like run: +1 passed, the new test; the skip lists differ only in the three reworded reasons and test_app_launch's pip-launcher skip, which comes from the 3.12 venv, not the change.)

- Risk: tests only, no app code. Invariance check: no (no run-path file touched). Windows: the pinned path is a WindowsPath under the temp state; settings._checkout gives Path(v).expanduser(), equal to it; no path literal, no encoding or line-ending change.
